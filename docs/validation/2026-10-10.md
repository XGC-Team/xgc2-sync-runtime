# Validation record, 2026-10-10

What was run for the first release of xgc2-module, with the commands, and what came out. Revision under test:
463aa9e on branch `issue-226-xgc2-module` (later commits only touch this record).

## Machine and toolchains

Ubuntu 20.04 x86_64 virtual machine, 8 vCPUs (Intel Xeon, 2.4 GHz), kernel 6.12.94, **shared with other build jobs**
(load average between 0.4 and 26 during this work), no root, no Docker. rustc 1.93.0 (stable) and 1.85.0 (the MSRV),
gcc 9.4 and, through the Bionic sysroot, gcc 7.5 with glibc 2.27, cmake 3.16, Python 3.8.

## glibc 2.27 (Ubuntu 18.04)

`scripts/bionic-build.sh` and `scripts/bionic-test.sh` source `scripts/bionic-env.sh`, which sets for cargo (target
`x86_64-unknown-linux-gnu`, its own `CARGO_TARGET_DIR=target/bionic`):

```text
CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_LINKER=/home/node/workspace/toolchains/bin/bionic-gcc
CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUSTFLAGS="-C link-arg=--sysroot=/home/node/workspace/toolchains/bionic-sysroot"
CC=.../bionic-gcc  CXX=.../bionic-g++                       # the test modules are compiled by gcc 7.5 too
CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUNNER="<sysroot>/lib/x86_64-linux-gnu/ld-2.27.so --library-path <sysroot>/lib/x86_64-linux-gnu:<sysroot>/usr/lib/x86_64-linux-gnu"
XGC2_HOST_RUNNER=<the same runner>                          # the command line tests start the binary this way
cargo build --locked -j3 --target x86_64-unknown-linux-gnu --bins
cargo test  --locked -j3 --target x86_64-unknown-linux-gnu
```

* The binary needs `GLIBC_2.25` at most (`objdump -T`); its interpreter is the system loader, and
  `LD_TRACE_LOADED_OBJECTS=1 ld-2.27.so --library-path ... xgc2-module-host` resolves libc, libdl, libpthread and
  libgcc_s inside the sysroot.
* All 102 tests pass with every test process (and the host binary of the command line tests) running on the glibc 2.27
  loader and libc of the sysroot.
* The same release binary is what the Debian packages ship, so one build serves 18.04, 20.04 and 24.04.

## Benchmark

`cargo bench --bench handoff` (`crates/xgc2-module-host/benches/handoff.rs`) runs a chain of three modules from
`tests/modules`: a producer with a 500 Hz period timer, a pass-through stage and a sink, both driven by their inputs.
Each module stamps its output with `now_ns()` right before `write_commit`; the next module computes
`step_ctx.now_ns - view.stamp_ns` when its step starts, so the numbers are measured by the modules with the host clock
(CLOCK_MONOTONIC) and include everything between commit and step start: dirty bit, queueing, worker wake-up if any,
step preparation. The first 500 samples are dropped; each configuration runs 15 s (about 7,500 samples). CPU is the
process CPU time from `getrusage`, thread wake-ups are the voluntary context switches of every thread from
`/proc/self/task`. The modules write no per-step reports in these runs. The host keeps its own histogram of the same
interval (oldest unprocessed commit to step start, measured inside the host, bucket error up to 12.5%); it reads 0.2 to
1 us lower than the module-side numbers, which also contain the module's time between stamping and committing and the
host's step preparation.

The machine was shared: the shipped scheduler ran while other jobs used about 28% of it, the shared-queue
variant while they used 47%. Absolute tails (p99.9, max) move with that background load; the wake-up counts and
CPU time barely do.

### Why a worker runs the tasks it makes runnable (run-next slot)

A copy of the tree with the run-next slot disabled (every runnable task goes through the shared queue and wakes an idle
worker) was measured in the same session, alternating with the shipped build:

| scheduler, 4 workers | producer -> stage p50 / p99 | stage -> sink p50 / p99 | producer -> sink p50 / p99 / p99.9 | process CPU | thread wake-ups/s |
|---|---|---|---|---|---|
| run-next slot (shipped) | 1.6 / 4.6 | 0.9 / 2.8 | 3.4 / 8.3 / 11.7 | 1.37% of one core | 1097 |
| shared queue only | 5.1 / 7.6 | 2.1 / 4.0 | 8.2 / 12.5 / 18.5 | 2.63% of one core | 2095 |

With the slot, a chain runs back to back on one worker: one worker wake-up per period (the one the timer thread causes),
against three for the shared queue (one per hop), half the CPU, and under half of the end-to-end latency. While this
comparison was prepared a defect showed up in the queue itself: the scheduler woke a worker while still holding the queue
lock, so every woken worker blocked on that lock again at once; with four workers that doubled the thread wake-ups of
the chain (2,099/s and 2.7% CPU on a quiet machine, instead of 1,097/s and 1.4%). The wake-up is now sent after the
unlock, and the shared-queue row above has the same fix.

### Reading the numbers

* Handoff is a few microseconds: a hop on one worker (run-next) costs about 1 us at the median, a hop to another worker
  about 5 us when it needs a wake-up; the chain of two hops stays below 10 us at p99 on a mostly idle machine.
* A 500 Hz chain of three modules costs 1 to 1.4% of one core including the timer thread and the context switches; an idle
  host with started instances costs about 0.1% and 100 wake-ups per second (the 10 ms watchdog tick).
* The timer thread's wake-ups (about 500/s) and the worker wake-up per period are the floor of the thread-based design;
  merging the two would halve them but the design record asks for one timer thread with a deadline heap.
* Everything here is on a non-real-time kernel without isolation. Tail latency (p99.9 and max) under contention is
  dominated by the Linux scheduler, not by the host; deployments with hard requirements need CPU isolation and
  SCHED_FIFO for the worker threads, which the host does not set up (follow-up).

## What was not tested

* The GitHub workflows and the container-based package scripts (`ci.yml`, `release.yml`, `ci_build_host.sh`,
  `ci_package.sh`, `check_debs.py --installed`): no Docker or GitHub Actions here; the workflow files parse and the scripts
  they call were run as listed above. The arm64 binary and arm64 packages were not built.
* The binary on a real Ubuntu 24.04 or 18.04 machine (it was run on this host's glibc 2.31 and on the glibc 2.27 loader).
* Any real module, the ROS edge, Gazebo or xsim: the modules of the products are being written against this header.
* Sanitizers, Miri and loom (not installed offline), hangs inside `create`/`start`/`stop` (same watchdog, 5 s floor, no
  dedicated test), real-time scheduling.
