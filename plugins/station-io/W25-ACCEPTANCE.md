## Actual changes and deletions

* A partial request or unread response has one two-second server deadline.
  A trickling/stalled client no longer retains the single accepted stream
  indefinitely. Runtime `step()` keeps using nonblocking `poll()` and its
  existing warning log; no flight command is generated by timeout handling.
* The client uses one deadline across connect, request write, reply header and
  reply body. Nonblocking Linux Unix-socket connect fails instead of hanging
  on a full backlog. EINPROGRESS readiness is bounded; EAGAIN is not retried.
  Setting read/write timeouts must succeed, rather than silently ignoring errors.
* A well-formed status 0 keeps the existing `queued` stdout/exit-zero contract.
  Only status 1 is an explicit rejection. EOF, timeout, malformed UTF-8,
  oversize response or an unknown response status after sending produce
  `outcome unknown: ...; not retried; ...`, not a fabricated rejection.
* Bind no longer unlinks an existing endpoint, which could steal another live
  authority's pathname. Drop checks the recorded socket inode before unlinking
  an unrelated replacement. This is ordinary socket ownership, not a lock service.
* Rejection text is shortened on a UTF-8 boundary. Interrupted server reads
  retain their partial request instead of dropping it.

The binary frame, command tokens, command/mission capability checks, port IDs,
ABI exports, telemetry keys/rates and success stdout remain unchanged.
The existing low-file-descriptor idle-poll regression is preserved.

### Operational change for Root review

An occupied or stale command socket now causes activation to fail. Normal
`deactivate`/Drop removes the owned socket; after a crash, the existing owning
workflow/operator must first verify the old runtime is stopped and then remove
its stale pathname. Do not add blind `rm` before every launch, and do not
reintroduce automatic unlink in `bind`. Root must accept this restart boundary
and coordinate it with W23 before product consumption.

## Result semantics

| Observed result | What is known | What is not known |
| --- | --- | --- |
| `queued`, exit 0 | The station edge reported local host publication | Controller consumption, flight transition, takeoff or landing completion |
| `rejected: <reason>`, exit 1 | The station edge returned an explicit rejection | No assertion about unrelated prior commands or vehicle state |
| `connect: <reason>`, exit 1 | This client sent no request on this attempt | Whether a previous attempt had an effect |
| `outcome unknown: ...`, exit 1 | A transport/protocol failure occurred after attempting delivery | Whether this command was consumed or acted upon |

There is exactly one connection/request attempt. Never automatically retry a
flight action after an unknown result. Actual state comes independently from
controller/FCU telemetry. Retain stdout/stderr and the target identity in the
existing per-member Workflow/Process result, rather than inventing a new ledger.

## Added regressions

`tests/support/socket_acceptance.rs` is included by the socket module. It is
under `support/` deliberately: it is not a separate Cargo integration crate.
Its eleven tests cover occupied/stale/replaced paths; incomplete request and
pending-reply expiry; UTF-8 truncation; eight in-flight members with individual
queued/rejected/unknown outcomes; missing and partial replies; full backlog;
and invalid/missing paths. All endpoints are unique temporary Unix sockets.

The eight-member fixture starts eight real calls to `transact` and withholds
**every** response until all eight requests have arrived. It then returns five
queued results, one explicit rejection and two unknown outcomes, and checks
that no client reconnects. This checks the IPC edge under concurrent callers;
it does **not** implement or prove GCS Workflow fan-out, authority-to-controller
publication, vehicle motion, or eight-machine network/CPU performance.
